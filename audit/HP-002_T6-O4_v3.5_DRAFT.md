## 1. Vocabulary (carried forward)
tactical plan → conditional stage → action intent → accepted command bundle → occupied resource lease → queued command. Posture, airborne, grounded, frozen, incapacitated and recovery are **constraints**, not resources.

## 2. Resources and compatibility [ENG, adopted from Codex X-5]
Seven exclusive resources: `locomotion`, `ball_control_release`, `hands_reach`, `contact`, `takeoff`, `archer_draw`, `projectile_release`. A `pose` resource is not added without a concrete limb-conflict model.
| Action | Resources |
|---|---|
| run, cut, pursue, Keeper approach/step | `locomotion` |
| pass, shot, held-ball kick (prep and release) | `ball_control_release` |
| catch prep / standing reach | `hands_reach` |
| jump catch | `hands_reach + takeoff` (atomic) |
| Keeper launch save | `hands_reach + takeoff` (+ `locomotion` only when one atomic command includes a committed lead-in) |
| tackle / grab / brace | `contact`, or `locomotion + contact` (atomic) |
| Archer draw / release | `archer_draw` / `projectile_release` (release depends on a completed valid draw) |
| no-attempt, hold position without movement | none |
Compatibility (YES\* = only under an action-specific separability contract; BUNDLE = only as one atomic bundle): locomotion+ball_control_release YES\*; locomotion+hands_reach YES\*; locomotion+contact BUNDLE; locomotion+takeoff BUNDLE; hands_reach+takeoff BUNDLE; archer_draw+locomotion YES\*; projectile_release+locomotion YES\*; archer_draw→projectile_release atomic transition; ball_control_release+hands_reach NO; ball_control_release+contact NO; hands_reach+contact NO; takeoff+contact BUNDLE only. The table is data with an entry for every pair, checked for completeness and symmetry (SUP-15).
**Completeness rule (O4-3).** Seven resources give 21 unordered pairs. Default for every distinct pair is **NO**; the explicit overrides are exactly the YES\*, BUNDLE and atomic-transition pairs listed above. The nine pairs not named above are therefore NO: `ball_control_release+takeoff`, `ball_control_release+archer_draw`, `ball_control_release+projectile_release`, `hands_reach+archer_draw`, `hands_reach+projectile_release`, `contact+archer_draw`, `contact+projectile_release`, `takeoff+archer_draw`, `takeoff+projectile_release`. `NO` means the two resources cannot be held concurrently by separate commands. It does not prohibit a later, explicitly approved composite technique from introducing a new atomic bundle in a new registry version; until that versioned contract exists the v1 behavior is NO. SUP-15 checks the 21-pair table is total and symmetric.
**Queues.** Depth one per resource. A bundle is admitted atomically: all resources start, or the whole bundle queues. **Canonical transaction (O4-3):** the requested resources are processed in the fixed registry order (never by iterating the requested set); no resource receives a partial reservation; if any resource would fail, none is reserved and the bundle is queued or rejected as a whole. If a queued bundle loses any of its queue positions (replacement or invalidation of one component), the whole bundle gets one `queue_replaced` or `queue_invalidated` outcome and none of it runs. Dormant plan stages hold no queue position.

## 3. Plans and stages [ENG/BEH]
- **Foreground executable plan:** at most one per athlete by default (configuration). **Execution-producing stage:** at most one active. A stage may emit concurrent bundles only if they lease disjoint resources under a declared separability contract. Dormant guards and alternative opportunity assessments may coexist, hold no resource and emit no command. Selecting a new foreground plan supersedes the old with a `supersedes` edge and a disposition for each stage and bundle.
- **Opportunity assessment is not unbounded.** It stays inside the existing attention and option-generation model. The plan-count limit simply does not count option candidates.
- **PlanStageActivation record** [PROPOSED, from Codex 3.3]: `plan_id, stage_id, source_decision_id, source_observation_id, trigger: TriggerRef (tagged union: ExternalObservation(observation_id) | OwnCommittedOutcome(outcome_id)), activated_at, reaction_gate: Availability<ReactionGateId>, reaction_gate_satisfied_at: Availability<SimTime>, guard_evaluation, no_new_option_evaluation: true`. For an own-outcome trigger both availability fields read `not_applicable_own_outcome` and no timestamp is invented; for an external observation both resolve to the actual `ReactionGate`. The activated intent keeps the source `source_decision_id`, gets a new `intent_id`, and cannot be backdated. Both the selecting view and the triggering observation are retained.
- **Reaction timing service (R-4, confirmed by Codex).** `CognitionTimingPolicy.reaction_gate(view, knowledge, stimulus_class, config, rng?) -> ReactionGate{reaction_gate_id, athlete_id, stimulus_class, trigger_observation_id, delivered_at, model_version, delay_ms, eligible_at, random_draws, unavailable_fields}`. Inputs are legitimate `AthleteView`/knowledge and immutable `MatchConfig.cognition_timing`, never authoritative hidden state. Any stochastic delay uses a registered cognition-owned stream and records its draws. Placement is engineering; the model values and rating mappings are behavioral parameters.
- **Activation rule** [BEH, recommended default; two trigger paths (O4-1)]:
```
ExternalObservationTrigger:
  activation_not_before = max(reaction_gate.eligible_at,
                              stage.absolute_not_before, other_temporal_guards)
OwnCommittedOutcomeTrigger:
  activation_not_before = max(outcome.actor_available_at,
                              stage.absolute_not_before, other_temporal_guards)
```
Ordinary cognition becomes eligible at `max(reaction_gate.eligible_at, next_decision_slot)`; an observation-triggered stage skips only the slot wait. It saves no reaction latency, hand preparation, reach, capacity, security or contention. A separate stage delay is an additional experimental delay, default 0.
- **Own-outcome triggers** [BEH, `RECOMMENDED_TEST_CANDIDATE`, J-3]: A's preselected cut activates at A's committed release outcome as available to A (`actor_available_at`, through own-action feedback with null latency by default), with **no added ordinary reaction delay**. The release is the plan's own causal outcome and A already chose the cut. This reverses my earlier conservative default, on Codex's argument. Gate C includes an arm that charges the ordinary reaction delay for comparison. External return-pass observation always uses the `ReactionGate`.
- **Latency caution (new).** If the B1 model adds a reaction delay on top of the cadence slot for ordinary decisions, athletes could become slower than B0 for unrelated reasons. Gate C therefore reports the distribution of ordinary decision latency (B0 versus B1) before any planned-versus-unplanned comparison is read.

## 4. Commitment events [adopted from Codex X-4; UNDECIDED cells stay open]
**Two boundaries.** The **cognitive revocation lock** is the point after which cognition may not revoke an intent. The **physical commitment** is the first irreversible physical execution event. Intent selection and command acceptance are simply earlier stages. Commitment is by ordered physical events and coincident batches, not by whole-tick inclusion.
| Action | Cognitive revocation lock | Physical commitment | Status |
|---|---|---|---|
| Locomotion / cut | none for the remainder; future locomotion stays supersedable | each committed integration result is irreversible | KEEP boundary, CHANGE ownership |
| Pass / shot (default) | `prep_started` | `ball_release_committed` (atomic carrier-to-flight mutation, B0 release 1077-1095) | recommended test candidate; physical boundary retained |
| Pass abort (experimental) | approved abort-window close | `ball_release_committed` | experimental only |
| Historical kick (B0 adapter) | `prep_started` (the B0 controller exposes no cognitive abort thereafter); the pre-preparation revocation state is `legacy_not_exposed` | the historical ball-release/strike transfer event (B0 release 1077-1095); **not tucked in B0** | preserved as B0 evidence only; no B1 kicking policy is inferred from it |
| Catch / reach | declared irreversible reach phase, if any | committed hand/body contact batch | ownership changed |
| Jump / Keeper launch | declared takeoff lock, if any (policy declared per command) | `takeoff_impulse_committed` | KEEP boundary, CHANGE ownership |
| Keeper step save | future steps supersedable | irreversible at committed hand/body contact | CHANGE ownership |
| Tackle / hold | unresolved | unresolved contact/grip/impulse event | **UNDECIDED** (technique) |
| Archer draw / release | draw revocable until release | `arrow_released_free_of_bow` | owner principle; see §4a |
| Keeper no-attempt | none | none (no command) | KEEP |
UNDECIDED rows fail validation (SUP-17) until resolved or explicitly waived as out of scope for the scenarios run.

### 4a. Archer ownership chain (Codex-confirmed, conditional on the owner record)
1. Cognition selects draw, aim, hold and release intentions from legitimate observation and belief.
2. Motor Control refuses **physical infeasibility only** (body or equipment cannot execute, no usable loaded Arrow, draw incomplete, authoritative incapacity). It does not adjudicate target, lane or timing legality and does not retarget.
3. A draw is revocable before release; aborting it frees `archer_draw` and spends no ammunition.
4. At `arrow_released_free_of_bow` PHY atomically creates the release outcome and decrements loaded ammunition. If the event does not commit, no ammunition is spent.
5. RULES then evaluates legality from the same authoritative snapshot as a causal child of the release outcome. An illegal release still spends the Arrow. It is never presented as an MC rejection.
**Normalized S7 wording (the unqualified phrase "not live" is retired).**
- **B1, pre-release blocker:** authoritative `play_state = stopped`, already effective in the common pre-event snapshot, blocks release; no arrow is released and no ammunition is spent. The existing Hunt rule (Archers cannot draw or fire until the ball has left the centre circle; nothing drawn, no ammo, no foul) is a member of this family for Archers.
- **B1, post-release legality:** a distinct legality condition first effective at or after physical release is evaluated afterward; ammunition remains spent.
- **B0 adapter:** preserves the legacy spend-before-`not_live`-check ordering independently (monolith 1756-1777).
**A2 (illegal-arrow consequences)** are the ruleset's minor-foul rule for a foul by the defence, cited in `HP-002_S6_S7_OPERATIONALIZATION.md` §2 (v0.3 [C] text if adopted, B0 code for the historical ruleset), and depend on R-RS. Advantage for an Archer foul: recommended default none (B0 behavior); rulebook 11.2/11.3 not readable from the repository.
**Feasibility vs legality (O4-8).** Body or equipment capability, no usable loaded arrow, and incomplete draw are **pre-release physical infeasibility** (MC refuses). An independently defined rules speed cap or minimum release interval is **post-release legality only if the rulebook defines it that way**; no such limit is defined in the sources I can read (A3). RULES never authorizes a physically impossible command, and MC never adjudicates a merely illegal but physically executable release.
**Release-error draws.** They occur only under the approved MC sampler contract. The fixed-draw fixture distinguishes `rejected_before_execution` (no release draw) from `release_committed_then_illegal` (draw consumed).
**Approved policy (S5 to S7):** A1 an illegal released arrow is nullified at release (no flight, no strike). A2 ammunition spent, illegal call, minor foul; restart, scoring and clock consequences are the ruleset's minor-foul rule for a foul by the defence (see above). A3 pre-release blockers are physical infeasibility and an already-effective `play_state = stopped` (including the Hunt restriction); a rules-only speed or release-interval limit is post-release legality only if the rulebook defines it so (none is defined in the sources I can read). If the external rulebook text conflicts with this, it returns to the owner.

## 5. Coincident-event resolution [ENG]
1. Advance to the earliest candidate sim time. 2. Capture one authoritative pre-event snapshot. 3. Collect all candidates from it. 4. Drop those invalid under the snapshot and resource contracts. 5. Order by causal dependency. 6. For same-state writers without a dependency, apply the versioned pair rule below, or a simultaneous multi-contact solve. 7. Commit one atomic batch. 8. Assign `batch_seq`; emit outcomes; release or transition leases. 9. Evaluate plan guards, then open timing-eligible cognition after the batch.
`batch_seq` is replay identity and batch chronology only. Actor ID, input order, hash-map order and telemetry order never decide a physical result. Candidate input permutations must yield identical state, events, RNG consumption and causal IDs (CE-1).
**Pair table v0** (preservation evidence from B0 line 2346 is not automatic B1 approval):
| Coincident candidates | Proposed resolution | Status |
|---|---|---|
| effective safety/administrative stop vs command | reject command | KEEP |
| strip / possession loss vs held-ball release | loss first; release rejected | B0-compatible [ENG] |
| grounding / tackle outcome vs held-ball release | grounding first; voluntary release rejected | B0-compatible [ENG] |
| freeze-causing Arrow impact vs release/takeoff/contact | impact first; revalidate | B0-compatible [ENG] |
| secure acquire vs unsecured touch/parry on same ball | acquire first; touch rejected | B0-compatible [ENG] |
| opponents secure-acquire same resolved instant | contested/joint control | B0 adapter: integer-ms bucket; native B1: exact canonical `EventTime` equality (no tolerance) |
| independent simultaneous body contacts | one multi-contact solve from common snapshot | REQUIRED [ENG] |
| contact impulse vs release at same instant | solve contact, then realize or reject release from resulting state | proposed [ENG/BEH] |
| contact/grounding vs takeoff | takeoff only if still eligible and feasible | proposed [ENG] |
| Arrow impact on ball vs hand/body contact | simultaneous solve or approved pair rule; never actor order | UNDECIDED until a simultaneous-contact contract exists |

Not defaulted to joint control (B0's joint-control convention is for opposing teams). | goal/boundary crossing vs secure catch (exact tie) | **Owner principle:** use NBA rules as the base. **Residual recommended defaults (mine, derived from the NBA text and B0; not owner rulings):** goal stands over a coincident catch; ball touching out-of-bounds floor/line stands over a coincident secure hold; player location by last floor contact | **owner-approved** (S3, S4) |
| clock/period/possession expiry vs release (exact tie) | **Owner principle:** use basketball jump-shot rules as the base. **Residual recommended defaults (mine):** a shot counts if the ball left the hand before expiry; a shot in flight stays live; exact-instant release counts; scope limited to shots; other releases are dead at expiry | **owner-approved** (S1, S2) |

**Simultaneity (Codex, adopted).** No floating-point epsilon or parity tolerance merges runtime events. Native candidates are coincident only when their canonical `EventTime{base_time_units, substep}` values are exactly equal. `substep` is the schema-versioned quantized time coordinate and **never an ordinal**. At schema freeze the base unit is named, and conversion must start from a deterministic exact or fixed-point source representation (or a parity-specified conversion); rounding an implementation-dependent floating value is insufficient for cross-platform identity. Two modes: the **B0 preservation adapter** keeps B0's integer-ms bucket and historical same-ms behavior exactly (including opposing same-ms secure acquires); the **B1/native boundary** uses `EventTime`, so events one representable unit apart are ordered, not merged. T3's ±1 ms figure applies only to comparing a native trace with a tick-quantized reference.

## 6. Wind-up revocability [BEH]
**Default:** once release preparation starts, cognition cannot revoke it; authoritative physical and rules interruptions remain (the tuck is one). **Experimental arm:** cognition may abort at an eligible opportunity. If the arm is run, the abort is one atomic transaction that: cancels the pending release and due time; discards command-local wind-up progress; releases or transitions the `ball_control_release` lease into the configured recovery; ends the live wind-up signal at the abort time and records its termination (observers learn of the abort only through ordinary observation or communication delivery; information already delivered stays in their beliefs); emits a causal `aborted` outcome; evaluates dependent plan guards from it; consumes no release-error draws; leaves possession, locomotion, momentum, fatigue, contact and posture untouched. The recovery formula and factor exist only inside the arm and are experimental. **B0-VERIFIED:** the tuck is skipped for kicks, is not a cognitive act, and resets nothing else, so it cannot be cited as support for this arm.

## 7. Same-athlete conflicts, queue and inability (carried from v2, adjusted) [ENG]
Intents carry `(decided_at, decision_stage, intent_seq)` with `intent_seq` allocated in canonical pipeline order. Later stages do not win through generic `intent_seq` priority: a declared stage transition explicitly completes, supersedes, suspends or refines the prior stage and disposes of each affected bundle per the plan contract. Conflicting intents from different decisions in the same tick: higher `intent_seq` supersedes a revocable earlier one (`superseded_before_start`). Queue replacement never touches a committed command. A queued command is invalidated, with a reason and never silently, by a rules stoppage, possession loss, freeze, incapacitation, expiry, a precondition that no longer holds, or the blocker ending in a way the precondition forbids. Promotion re-checks preconditions only and does not refresh the target belief. Inability at acceptance: `rejected / infeasible_at_acceptance`. During execution: `interrupted` or `partial` / `execution_inability`; the plan's declared failure transition applies, and the whole plan is aborted (`plan_aborted`) only when no valid failure or alternative branch exists.

## 8. Self-knowledge types [BEH]
`MotorFeedback` (Motor Control only, command-local authoritative body projection), `SelfView.proprioception` (sensed own pose, motion, contact, fatigue symptoms), `AthleteKnowledge.self` (stable capability and technique estimates). Cognition cannot import `MotorFeedback` or authoritative state; MC cannot accept `SelfView`. Hidden reserves, exact ratings, hidden timers and implementation-only impairments are not exposed. Default: zero error and latency on sensed pose and motion, and zero-error capability estimates labelled placeholders, not a canon model. Named self-perception parameters replace the IQ sweep.

```
PolicyRef { policy_family, policy_id, policy_version, status: resolved | unresolved | unsupported }
CommitmentPolicyRef            : PolicyRef   // unresolved tackle/contact commitment
CoincidentResolutionPolicyRef  : PolicyRef   // Arrow / ball / hand simultaneous contact

ConformanceProfile {
  profile_id, schema_version, ruleset_version,
  supported_policies:        List<PolicyRef>        // only status == resolved
  excluded_scenario_classes: List<ScenarioClass>    // explicitly out of v1 conformance
}
UnresolvedOutcome {
  code: UNRESOLVED_COMMITMENT | UNRESOLVED_COINCIDENT | UNRESOLVED_POSSESSION_ASSIGNMENT,
  policy_ref, scenario_class_id, causal_parent
}
```
Rules: (1) the v1 profile lists tackle commitment, Arrow/ball/hand ties and same-team assignment as `unresolved` and puts their scenario classes in `excluded_scenario_classes`; (2) a scenario in an excluded class is rejected at scenario selection, not run; (3) if a run nonetheless reaches a case that needs an unresolved or unsupported policy, PHY emits `UnresolvedOutcome` and fails the run loudly; **no outcome is fabricated**; (4) policy ids and versions and the profile hash enter the replay digest input (O5 §3), so a changed policy changes the replay identity; (5) adding or changing a policy is a new profile version, not a change to the frozen core types. Tests: EXT-1 an excluded scenario is rejected at selection; EXT-2 an unresolved case at runtime yields `UnresolvedOutcome` and no state mutation; EXT-3 an unsupported policy version fails validation; EXT-4 the profile hash changes the replay id; EXT-5 resolving a policy adds a new profile version and leaves core type hashes unchanged.
