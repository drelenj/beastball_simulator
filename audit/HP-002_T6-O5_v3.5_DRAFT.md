## 1. What changed and why
Codex was right on the main point, and I checked it against the T6 evidence. T6 `TYPED_CONTRACTS.md` §10 gives the conceptual ID as `<match>/<tick-or-event-seq>/<actor>/<domain>/<local-seq>/<kind>`, and T6 spec §8.3 derives IDs from "match ID, authoritative tick or event sequence, actor, domain, and a monotonically allocated local sequence". My v2/v3 dropped the tick/event sequence from the ID and moved chronology into a neighboring field. That regressed the accepted form. v3.1 restores all of the required fields in identity and keeps `order` only as a sorting convenience.
Changes: (1) full structured `CausalId` (O5-1); (2) 128-bit replay namespace with full provenance retained (O5-2); (3) complete actor/entity registry and fixed-width option sequence (O5-3); (4) defined batch context for non-physical records (O5-4); (5) ID-12 replaced (O5-5); (6) simultaneity clarified (O5-6).

## 2. CausalId (O5-1)
```
CausalId {
  schema_version      # "beastball-causal-v1"
  replay_id           # §3
  tick_seq            # outer step counter
  event_batch_seq     # §5
  sim_time            # canonical EventTime (below); integer ms in the B0 adapter projection
  processing_stage    # observe, belief, decide, intent, command, physics, rules
  actor_or_entity     # §4
  domain
  local_seq           # scope below
  kind
}
```
Canonical string projection (every component versioned, escaped, and fixed width where numeric):
`<replay>/k<tick>/b<batch>/t<sim_time>/<stage>/<actor_or_entity>/<domain>/<local_seq>/<kind>`
`order` may duplicate the chronological fields for efficient sorting. It is a convenience: it neither replaces the identity components nor decides physics. Consumers do not sort ID text (ID-10).
**`EventTime`** = `{base_time_units: UInt53, substep: UInt32}`. `substep` is a **versioned, deterministically quantized within-base-unit time coordinate**, not a record sequence number: proposed schema rule, the fractional part of the base unit is scaled by 2^32 and rounded to nearest with ties to even, with overflow carried into `base_time_units`; the conversion and rounding rule are named in `beastball-causal-v1`. Candidates at the same physical instant, after the solver's declared quantization, share the same value; values one unit apart are ordered. Comparison is lexicographic on (`base_time_units`, `substep`). String form: `<base, fixed width>.<substep, fixed width>`. Range checks apply per component. The B0 adapter projection is `substep = 0` with `base_time_units` in integer ms.
**`local_seq` scope:** local to `(replay_id, tick_seq, event_batch_seq, processing_stage, actor_or_entity, domain)`. It increments in canonical pipeline/allocation order, independent of telemetry and input-container order. `kind` stays a separate component and the sequence does not reset by kind, so uniqueness is by (scope, `local_seq`).
**Numeric widths** are specified by `beastball-causal-v1`, not here. Overflow fails (`id_range_exceeded`); no field widens mid-run.
**`order`** is a structured, non-authoritative record `(tick_seq, event_batch_seq, sim_time, processing_stage, entity_rank, local_seq)` for efficient sorting. `entity_rank` appears only here, as a serialization and allocation rank; it is not a CausalId component and never decides a physical result.
**`processing_stage` registry (declared, ordered):** `observe, belief, decide, intent, command, physics, rules, system`. **`domain` registry:** `carry pass shot move pursue receive catch tackle block jump keeper archer projectile rest rule physics environment system plan batch`. `receive` is the delivered-observation and preparation phase of a catch, distinct from the resolved `catch` outcome. All Arrow records use `projectile` (flight, impact) or `archer` (draw, release intention). **Configuration is referenced provenance only** (replay digest input and run manifest) and has no causal-ledger record, so there is no `config` domain, stage or kind.
**Draw records (O5-7).** A `draw` record has `kind = draw` and **inherits the domain and processing stage of the subsystem consuming it**; the stream identity is recorded in a separate field (`rng_stream_id`). The post-step RNG-vector hash is a `system` record and never replaces the owner of individual draws.
**`kind` registry (declared):** `obs bel dec opt int act cmd ingress out phys_event rule rules_event reaction_gate draw event_batch rng_vector_hash comm`. Distinctions: `out` is a typed `PhysicalOutcome` resolving a command or intent; `phys_event` is an emergent physical event that is not itself a command outcome; `rule` is a rule evaluation or decision; `rules_event` is a committed authoritative rules-state mutation. Every T6 record type must map to exactly one (processing stage, domain, kind); a record with no mapping fails the schema check (ID-19), never an ad hoc string.

### 2a. Causal-ledger record registry (valid; exhaustive for v3.5, frozen at schema freeze)
**Ledger records** get a CausalId. **Value and embedded types** do not: `Vec2`, `Vec3`, `Velocity3`, `Estimate<T>`, `Availability<T>`, `UnavailableReason`, status enums, `MatchConfig` (provenance only, referenced by hash), `SimState` (referenced by snapshot hash), and an `AthleteView` that is only a part of its `ObservationFrame`.

|---|---|---|---|---|
| `ObservationFrame` (and `AthleteView` when emitted independently) | observe | domain of the athlete activity served; `receive` for catch preparation | `obs` | `ATHLETE:<id>` |
| communication delivery (only if emitted independently of its observation) | observe | domain of the message | `comm` | `ATHLETE:<id>` |
| belief revision | belief | domain of the owning decision | `bel` | `ATHLETE:<id>` |
| `ReactionGate` | decide | domain of the stimulus class | `reaction_gate` | `ATHLETE:<id>` |
| `OptionTrace` | decide | domain of the option | `opt` | `ATHLETE:<id>` |
| `DecisionTrace` | decide | domain of the selected option | `dec` | `ATHLETE:<id>` |
| `ActionIntent` | intent | domain of the action | `int` | `ATHLETE:<id>` |
| `PlanStageActivation` | intent | `plan` | `act` | `ATHLETE:<id>` |
| `MotorCommand` | command | domain of the action | `cmd` | `ATHLETE:<id>` |
| `CommandIngressResult` (if emitted) | command | domain of the action | `ingress` | `ATHLETE:<id>` |

Every row is exactly one declared (stage, domain, kind). No row uses an undeclared value, no placeholder spellings exist, and `ReactionGate` has one mapping. ID-19 validates this registry once frozen.
**Proposed numeric widths (for the schema freeze, to confirm with Codex):** `tick_seq`, `event_batch_seq`, `base_time_units` as 16-digit zero-padded decimal (UInt53 range); `substep` and `local_seq` as 10-digit zero-padded decimal (UInt32); overflow fails and never widens mid-run. Final enum spellings are frozen with the registry.

## 3. Replay namespace and provenance (O5-2)
`replay_id` = at least the first **32 hex characters (128 bits)** of the SHA-256 over a canonical digest input. The run manifest retains the **full SHA-256 and the canonical digest input**. Digest input includes, directly or through a verified canonical config hash (and, from O4 v3.5 §11, the conformance profile hash with its policy ids and versions): frozen source identity/commit; engine and interface versions; schema and ruleset version; resolved configuration and feature flags; seed and random-stream controls and registry version; initial roster and state inputs that affect execution.
No collision-immunity claim. Collision detection compares the full retained digests and provenance. `run_instance_id` (run, attempt, start time, host) stays only in the run manifest and telemetry envelope, never in a CausalId.

## 4. Actor/entity registry (O5-3)
`ATHLETE:<id>`, `BALL`, `ARROW:<id>`, `RULES`, `ENV`, `MATCH`, `SYSTEM:<versioned-id>`. Registries are versioned; enum and path components are escaped. Physical roots (passive collision, bounce, arrow flight, clock-based rule violation, injury threshold, rules-state change) use `BALL`, `ARROW`, `ENV`, `RULES` or the affected `ATHLETE` and carry `emergent_cause`, never a fabricated cognitive chain. In the B0 tier, ancestry that exists but was not exposed reads `legacy_not_exposed`. An outcome may name a `causal_intent` only if it resolves and `intent.decided_at <= outcome.started_at`.

## 5. Batch context for non-physical records (O5-4)
- `event_batch_seq = 0` denotes the initialized authoritative state before the first committed event batch.
- Each committed physical/rules event batch (O4 v3.1 §5) takes the next match-wide `event_batch_seq`. Zero-time authoritative state commits receive their own batch sequence.
- Observations, beliefs, decisions, intents and commands carry the **latest committed batch whose post-state they are based on**. Cognition produced from an outcome carries that outcome's batch.
- No intent is placed in a future physical batch.

## 6. Simultaneity and serialization (O5-6)
All physical candidates in one resolved batch share the batch identity. `processing_stage`, `entity_rank` and `local_seq` canonically serialize already-resolved records and allocate IDs; they do **not** make simultaneous physical effects sequential and never decide a physical result. `batch_seq`, `entity_rank` and ID text never choose among coincident candidates (CE-1, CE-4).

**Committed-ID allocation (O5-9, O5-11).** Candidates inside a coincident set carry non-ID provisional handles and stay outside the committed ledger until the set is resolved (O4 v3.5 §5). After resolution, records are grouped by the `local_seq` scope tuple `(replay_id, tick_seq, event_batch_seq, processing_stage, actor_or_entity, domain)`. Within each scope, `local_seq` is allocated from a **schema-owned semantic key that does not contain `local_seq`** and uses neither provisional handles nor input-container order:
`semantic_key = (kind_rank, causal_parent_id, type_specific_slot, multiplicity_index)`
`kind_rank` is the declared kind's fixed rank in the registry. `causal_parent_id` is the identity of the record's declared parent. `type_specific_slot` is per record family: `PhysicalOutcome` the command id; `phys_event` (event-type rank, subject entity, object entity); `rules_event` (rule id, subject); `draw` (stream id, purpose, ordinal within the stream); `dec` (athlete, decision-opportunity time); `obs` (athlete, capture time, sensor channel). A residual exact duplicate without an explicit `multiplicity_index` is rejected, never numbered arbitrarily. This makes ID-13 and ID-23 implementable.

## 7. Allocation, range, hashing
Allocated in core execution, independent of telemetry, as a pure counter: no draws, no I/O, no wall time, no UUID, no hash-map order, no host or run identity. Adding the allocator is an instrumentation change and triggers the rc2 §8 NI re-runs. `EventTime` components and counters are unsigned integers within their declared widths (`base_time_units` ≤ 2^53−1); exceeding a limit raises `id_range_exceeded` and never wraps, saturates or truncates.
CT-4: a versioned registry lists all cognition-owned streams; the full registered vector is hashed once after each committed outer step; the prior post-vector is reused as the next pre-vector; stream creation or removal is recorded as an explicit `unavailable→hash` or `hash→unavailable` transition; hashing neither instantiates minds, draws, nor iterates a mutating unordered store.

## 8. Cross-arm comparison (O5-5)
Identical causal execution reproduces identical CausalIds. If an inserted event changes tick or batch chronology, affected IDs change. This replaces my earlier insertion-stability goal. Gate C arm correlation uses explicit parentage and an optional typed `comparison_anchor` that is non-authoritative, may be unavailable, and can never determine chronology, arbitration or any physical outcome.
