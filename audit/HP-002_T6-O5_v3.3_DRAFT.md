## 2. CausalId (O5-1)
```
CausalId {
  schema_version      # "beastball-causal-v1"
  replay_id           # §3
  tick_seq            # outer step counter
  event_batch_seq     # §5
  sim_time            # canonical EventTime (below); integer ms in the B0 adapter projection
  processing_stage    # observe, belief, decide, intent, command, physics, rules
  actor_or_entity     # §4
  domain
  local_seq           # scope below
  kind
}
```
Canonical string projection (every component versioned, escaped, and fixed width where numeric):
`<replay>/k<tick>/b<batch>/t<sim_time>/<stage>/<actor_or_entity>/<domain>/<local_seq>/<kind>`
`order` may duplicate the chronological fields for efficient sorting. It is a convenience: it neither replaces the identity components nor decides physics. Consumers do not sort ID text (ID-10).
**`EventTime`** = `{base_time_units: UInt53, substep: UInt32}`. `substep` is a **versioned, deterministically quantized within-base-unit time coordinate**, not a record sequence number: proposed schema rule, the fractional part of the base unit is scaled by 2^32 and rounded to nearest with ties to even, with overflow carried into `base_time_units`; the conversion and rounding rule are named in `beastball-causal-v1`. Candidates at the same physical instant, after the solver's declared quantization, share the same value; values one unit apart are ordered. Comparison is lexicographic on (`base_time_units`, `substep`). String form: `<base, fixed width>.<substep, fixed width>`. Range checks apply per component. The B0 adapter projection is `substep = 0` with `base_time_units` in integer ms.
**`local_seq` scope:** local to `(replay_id, tick_seq, event_batch_seq, processing_stage, actor_or_entity, domain)`. It increments in canonical pipeline/allocation order, independent of telemetry and input-container order. `kind` stays a separate component and the sequence does not reset by kind, so uniqueness is by (scope, `local_seq`).
**Numeric widths** are specified by `beastball-causal-v1`, not here. Overflow fails (`id_range_exceeded`); no field widens mid-run.
**`order`** is a structured, non-authoritative record `(tick_seq, event_batch_seq, sim_time, processing_stage, entity_rank, local_seq)` for efficient sorting. `entity_rank` appears only here, as a serialization and allocation rank; it is not a CausalId component and never decides a physical result.
**`domain` registry:** `carry pass shot move pursue receive catch tackle block jump keeper archer projectile rest rule physics environment system config plan batch`. `receive` is the delivered-observation and preparation phase of a catch, distinct from the resolved `catch` outcome. All Arrow records use `projectile` (flight, impact) or `archer` (draw, release intention). `config` is reserved for configuration-derived causal roots and gates only.
**Draw records (O5-7).** A `draw` record has `kind = draw` and **inherits the domain and processing stage of the subsystem consuming it**; the stream identity is recorded in a separate field (`rng_stream_id`). The post-step RNG-vector hash is a `system` record and never replaces the owner of individual draws.
**`kind` registry:** `obs bel dec opt int cmd out act rule draw reaction_gate event_batch phys_event rules_event`. Distinctions: `out` is a typed `PhysicalOutcome` resolving a command or intent; `phys_event` is an emergent physical event that is not itself a command outcome; `rule` is a rule evaluation or decision; `rules_event` is a committed authoritative rules-state mutation. Every T6 record type must map to exactly one (processing stage, domain, kind); a record with no mapping fails the schema check (ID-19), never an ad hoc string.

## 3. Replay namespace and provenance (O5-2)
`replay_id` = at least the first **32 hex characters (128 bits)** of the SHA-256 over a canonical digest input. The run manifest retains the **full SHA-256 and the canonical digest input**. Digest input includes, directly or through a verified canonical config hash: frozen source identity/commit; engine and interface versions; schema and ruleset version; resolved configuration and feature flags; seed and random-stream controls and registry version; initial roster and state inputs that affect execution.
No collision-immunity claim. Collision detection compares the full retained digests and provenance. `run_instance_id` (run, attempt, start time, host) stays only in the run manifest and telemetry envelope, never in a CausalId.

## 4. Actor/entity registry (O5-3)
`ATHLETE:<id>`, `BALL`, `ARROW:<id>`, `RULES`, `ENV`, `MATCH`, `SYSTEM:<versioned-id>`. Registries are versioned; enum and path components are escaped. Physical roots (passive collision, bounce, arrow flight, clock-based rule violation, injury threshold, rules-state change) use `BALL`, `ARROW`, `ENV`, `RULES` or the affected `ATHLETE` and carry `emergent_cause`, never a fabricated cognitive chain. In the B0 tier, ancestry that exists but was not exposed reads `legacy_not_exposed`. An outcome may name a `causal_intent` only if it resolves and `intent.decided_at <= outcome.started_at`.

## 5. Batch context for non-physical records (O5-4)
- `event_batch_seq = 0` denotes the initialized authoritative state before the first committed event batch.
- Each committed physical/rules event batch (O4 v3.1 §5) takes the next match-wide `event_batch_seq`. Zero-time authoritative state commits receive their own batch sequence.
- Observations, beliefs, decisions, intents and commands carry the **latest committed batch whose post-state they are based on**. Cognition produced from an outcome carries that outcome's batch.
- No intent is placed in a future physical batch.

## 6. Simultaneity and serialization (O5-6)
All physical candidates in one resolved batch share the batch identity. `processing_stage`, `entity_rank` and `local_seq` canonically serialize already-resolved records and allocate IDs; they do **not** make simultaneous physical effects sequential and never decide a physical result. `batch_seq`, `entity_rank` and ID text never choose among coincident candidates (CE-1, CE-4).

**Candidate ID allocation (O5-9).** Candidate records inside a coincident set carry non-ID provisional handles and stay outside the committed causal ledger until the set is resolved (O4 v3.3 §5). Committed IDs are allocated at batch commit, in canonical order by (`processing_stage`, `entity_rank`, `local_seq` scope), never by raw input-container order. This makes ID-13 implementable.

## 7. Allocation, range, hashing
Allocated in core execution, independent of telemetry, as a pure counter: no draws, no I/O, no wall time, no UUID, no hash-map order, no host or run identity. Adding the allocator is an instrumentation change and triggers the rc2 §8 NI re-runs. `EventTime` components and counters are unsigned integers within their declared widths (`base_time_units` ≤ 2^53−1); exceeding a limit raises `id_range_exceeded` and never wraps, saturates or truncates.
CT-4: a versioned registry lists all cognition-owned streams; the full registered vector is hashed once after each committed outer step; the prior post-vector is reused as the next pre-vector; stream creation or removal is recorded as an explicit `unavailable→hash` or `hash→unavailable` transition; hashing neither instantiates minds, draws, nor iterates a mutating unordered store.

## 8. Cross-arm comparison (O5-5)
Identical causal execution reproduces identical CausalIds. If an inserted event changes tick or batch chronology, affected IDs change. This replaces my earlier insertion-stability goal. Gate C arm correlation uses explicit parentage and an optional typed `comparison_anchor` that is non-authoritative, may be unavailable, and can never determine chronology, arbitration or any physical outcome.
