## 3. Required v3.3 corrections

### O4-6 — Make historical-kick boundaries explicit

Replace `same / same` with named boundaries. For the B0 adapter, state explicitly that cognition has no abort after preparation starts and that physical commitment is the historical ball-release/strike transfer event. Do not infer a B1 kicking policy from that preservation rule.

### O4-7 — Remove the `not live` contradiction

O4 currently says an already-effective administrative stoppage may block release before execution, then classifies `not live` as post-release legality because B0 spends ammunition before its check. Those are different contracts and must not be collapsed.

- **B0 adapter:** preserve the observed legacy ordering: release attempt consumes ammunition before the legacy not-live legality check, with no Arrow object in the illegal path.
- **B1 contract:** keep the exact pre-release blocker list under RESIDUAL-A3. The recommended engineering default should be that an authoritative stoppage already effective in the common pre-event snapshot blocks release; a legality condition arising at or after release is a post-release rule evaluation.

Historical implementation order is evidence, not by itself a canon ruling for the B1 boundary.

### O4-8 — Split physical feasibility from rule legality for speed and reload

“Speed” and “reload” are currently too broad:

- body/equipment capability, no usable loaded arrow, and incomplete draw are pre-release physical infeasibility;
- an independently defined rules speed cap or minimum release interval is post-release legality only if the rulebook actually defines it that way.

Do not let RULES authorize a physically impossible command, and do not let MC adjudicate a merely illegal but physically executable release.

### O4-9 — Add Archer boundary acceptance tests

Add explicit fixtures proving:

1. draw abort: no release, no ammunition spent, no release-error draw;
2. pre-release physical/authoritative blocker: no release and no ammunition spent;
3. committed release: one release outcome, exactly one ammunition decrement, and only the approved MC release draws;
4. committed but illegal release: ammunition still spent and the legality result is a causal child of the release;
5. unresolved A1/A2/A3 cases fail or are explicitly excluded, never silently defaulted;
6. the B0 adapter preserves its historical not-live ordering independently of the future B1 policy.

### O5-6 — Define `EventTime.substep` as time, not allocation order

`UInt32` gives a width but not semantics. Define `substep` as a versioned, deterministically quantized within-base-unit time coordinate (or equivalent exact fractional coordinate), not a record sequence number. Candidates at the same physical instant must share the same value; values one unit apart are ordered. Specify the conversion/rounding rule in the schema. This is necessary for exact simultaneity and input-permutation invariance.

### O5-7 — Correct RNG draw domain ownership

Delete “`config` covers ... causal draw records.” A draw uses `kind=draw` and inherits the domain and processing stage of the subsystem consuming it, with stream identity recorded separately. `config` is reserved for configuration-derived causal roots/gates. The post-step RNG-vector hash may use a defined `system` record, but it must not erase the owner of individual draws.

### O5-8 — Make the record-type registry truly total

The present descriptions do not uniquely distinguish `out` from `phys_event` or `rule` from `rules_event`. Before freeze, publish a total versioned mapping for every T6 record type across **processing stage, domain, and kind**. Recommended distinctions:

- `out`: typed `PhysicalOutcome` resolving a command/intent;
- `phys_event`: emergent physical event not itself a command outcome;
- `rule`: rule evaluation/decision;
- `rules_event`: committed authoritative rules-state mutation.

ID-19 should validate this complete three-field mapping, not merely domain/kind.

### O5-9 — State when candidate IDs are allocated

To make ID-13 implementable, candidate records must either be canonically ordered before ID allocation or remain outside the committed causal ledger until the coincident set is resolved. Raw input-container order may never allocate committed IDs.

## 4. Freeze and authorization sequencing
