## 3. Confirmation of the Archer consequence

Conditional on the owner direction being quoted accurately, the consequence is **mostly confirmed**, with two residual contracts required.

### 3.1 Confirmed ownership chain

1. **Cognition** selects draw, aim, hold, and release intentions from legitimate observation/belief.
2. **Motor Control** may reject physical infeasibility only: for example, the body/equipment cannot execute, no usable loaded Arrow exists, draw is incomplete, or an authoritative incapacity prevents execution. MC does not adjudicate target/lane/timing legality or silently retarget.
3. A draw is revocable before release. Aborting the draw releases `archer_draw`, preserves already-expended physical effort as history, and spends no ammunition.
4. At `arrow_released_free_of_bow`, **PHY atomically** creates the projectile/release outcome and decrements loaded ammunition. If that event does not commit, ammunition is not spent.
5. **RULES then evaluates legality** as a causal consequence of the committed release from the same authoritative snapshot. An illegal release still spends the Arrow.
6. The rule outcome links to the release outcome as its causal parent; it must not be retroactively presented as MC rejection.

This is compatible with the intended cognition → MC → PHY → RULES split and with preserving the historical B0 ammo-before-later-checks behavior in the adapter.

### 3.2 Residual Archer decisions/contracts

The owner direction as quoted does not by itself answer:

- whether an illegally released Arrow remains live and can physically strike/freeze a target before or alongside the sanction;
- the sanction, restart, scoring, and advantage consequences of the illegal release;
- which pre-existing administrative/safety states prevent command execution entirely, as distinct from play legality judged after release;
- whether release-error RNG draws are consumed when a command reaches MC but is stopped before physical release.

Recommended rule:

- safety/administrative constraints already effective before the release may block execution through CommandIngress/PHY constraint validation;
- a live-play target/lane/timing violation is adjudicated after release;
- MC release-error draws occur only under the approved MC sampler contract and the fixed-draw fixture must distinguish `rejected_before_execution` from `release_committed_then_illegal`.

Do not infer the illegal Arrow's continued physical effects or sanction from the ammo rule. Record them explicitly in the rule contract.

## 4. Final required T6-O4 v3.1 edits

### O4.1 — Remove the commitment-table regression

Section 4 correctly withdraws the phrase that wind-up “is not committed by cognition,” but the Pass/Shot table row still contains:

> wind-up is not committed by cognition under the default

Delete it. Under the default, the cognitive revocation lock is `prep_started`; the physical commitment is `ball_release_committed`.

The section also says both boundaries are defined, but the table still contains only `Commitment event` and `Class`. Use the promised two-boundary table:

| Action | Cognitive revocation lock | Physical commitment | Status |
|---|---|---|---|
| Pass/shot default | `prep_started` | `ball_release_committed` | recommended test candidate / physical boundary retained |
| Experimental pass abort | approved abort-window close | `ball_release_committed` | experimental only |
| Jump/Keeper launch | declared takeoff lock, if any | `takeoff_impulse_committed` | lock policy declared per command |
| Catch/reach | declared irreversible reach phase, if any | committed hand/body contact batch | ownership changed |
| Tackle | unresolved | unresolved contact/grip/impulse event | `UNDECIDED` |
| Archer draw/release | draw revocable until release | `arrow_released_free_of_bow` | conditional on owner record |

Remove the duplicated sentence beginning `"Commitment" = intent selection...`; intent selection and command acceptance are simply earlier stages, not a second definition.

### O4.2 — Add unavailable semantics to `PlanStageActivation`

`reaction_gate_satisfied_at` is not applicable to an own-committed-outcome trigger. The record must not invent a timestamp.

Use:

```text
reaction_gate: Availability<ReactionGateId>
reaction_gate_satisfied_at: Availability<SimTime>
```

For own-outcome activation, both read `not_applicable_own_outcome`. For an external observation, both resolve to the actual `ReactionGate`.

Similarly, `trigger_observation_id_or_outcome_id` should be a typed union, not an untagged polymorphic field.

### O4.3 — Resolve stale simultaneity wording

The pair-table row for opposing secure acquires still says “native tolerance open.” Section 5 now resolves this correctly with exact canonical `EventTime` equality and no runtime epsilon.

Replace the stale status with:

> B0 adapter: integer-ms bucket; native B1: exact canonical EventTime equality.

This is not a tolerance question anymore.

### O4.4 — Keep same-team and Arrow multi-contact ties open

The corrected same-team row is accepted. Do not use joint control or entity rank implicitly. `Arrow impact on ball vs hand/body contact` also remains a physical-resolution decision and should stay `UNDECIDED` until a simultaneous-contact contract exists.

## 5. Final required T6-O5 v3.1 edits

### O5.1 — Define `local_seq` scope

`local_seq` is currently described only as “monotone, fixed width.” Define it as local to:

```text
(replay_id, tick_seq, event_batch_seq, processing_stage, actor_or_entity, domain)
```

It increments in canonical pipeline/allocation order and is independent of telemetry and input-container order. Because `kind` remains a separate ID component, the sequence should not reset by kind unless that different scope is explicitly selected and uniqueness is proven.

### O5.2 — Complete the domain and kind registries

The current actor/entity registry is accepted. The domain registry still needs at least explicit values for:

- `receive` (distinct from resolved catch where applicable);
- `environment`;
- `system`;
- `projectile` or an explicit statement that all Arrow records use `archer`/`physics`;
- any configuration/random domain used by causal draw or gate records.

The kind registry needs explicit representations for at least:

- `reaction_gate`;
- committed `event_batch`;
- physical/rules event when it is not adequately represented by `out`/`rule`.

Alternatively, document exact mappings proving the existing enums cover every T6 record. No record may fall back to an ad hoc string.

### O5.3 — Correct the `ReactionGate` ancestry test

ID-15 currently says both `PlanStageActivation` and `ReactionGate` resolve to a source decision, selecting view, and trigger. An ordinary `ReactionGate` exists before its resulting decision and therefore has no source decision.

Split the test:

- `PlanStageActivation` resolves to the source decision, selecting view, and trigger observation/outcome;
- `ReactionGate` resolves to the trigger observation/AthleteView, timing-model/config version, athlete, stimulus class, and any RNG draws; it may later be referenced by a decision or plan activation.

ID-6 should likewise require the full exposed chain `outcome → command → intent → decision → belief/view → observation`, not merely that the outcome “resolves to an observation.”

### O5.4 — Make `sim_time` and range language consistent

Section 2 defines `sim_time` as canonical `EventTime`, which may contain a base tick/ms plus a substep ordinal or fixed fraction. Section 7 then says `sim_time` is an integer in `0..2^53−1`.

Choose and specify a canonical representation, for example:

```text
EventTime {
  base_time_units: UInt53
  substep: UInt32
}
```

or one fixed-point integer with a declared scale. Define comparison and string serialization exactly. Range checks apply to each component or to the fixed-point integer, not ambiguously to an object.

The B0 adapter projection remains integer milliseconds.

### O5.5 — Define numeric widths and `order`

The canonical string says numeric fields are fixed-width but does not identify schema-owned widths. Exact widths may remain a later schema freeze item, but v3.1 should state they are specified by `beastball-causal-v1` and that overflow fails rather than widening mid-run.

Section 6 mentions `entity_rank`, but neither `CausalId` nor a structured `order` record defines it. Either:

- define `order` with `entity_rank` as a non-authoritative serialization field; or
- remove the reference.

It must never decide a physical result.

### O5.6 — Accepted O5 architecture

Subject to O5.1–O5.5, Codex confirms:

- full structured CausalId fields;
- canonical string projection;
- at least 128 replay bits plus full digest/provenance;
- replay identity separated from run-instance identity;
- BALL/ARROW/RULES/ENV/MATCH/SYSTEM roots;
- latest-committed-batch context for non-PHY records;
- no future-batch assignment;
- simultaneous physical batch membership separated from serialization;
- telemetry/RNG/I/O-neutral allocation;
- comparison anchors separated from causal identity;
- CT-4 one-post-vector hashing and stream availability transitions.

## 6. Behavioral-default process and authorization sequencing

The consolidated register is accepted as the right transparency mechanism, assuming it reflects the owner's standing process. No additional per-item gate is demanded during paper drafting.

However, the stated sequence—showing the register at Contract v1 freeze **with Gate C measurements attached**—cannot occur under the present authorization unless an intermediate implementation authorization is granted. Gate C measurements require some B1 behavior to be implemented and run; B1 implementation is currently unauthorized.

One of these sequences must be explicit:

### Sequence A — measurement before final freeze

1. keep Contract v1 draft open;
2. owner approves the register as experimental implementation candidates;
3. separately authorize bounded B1/Gate C implementation;
4. run Gate C and attach measurements;
5. owner freezes/approves final behavioral selections.

### Sequence B — interface freeze with provisional behavior

1. freeze only the typed interface/ownership/arbitration contract;
2. keep behavioral parameter selections explicitly provisional and versioned outside the frozen interface core;
3. separately authorize experimental B1 implementation;
4. run Gate C;
5. ratify a behavioral profile/addendum.

The drafts must not imply that measurements can precede implementation authority. Nothing in v3.1 or this review grants that authority.
